Executive summary

How to define the evaluation. Choose a recurring workload and define success, tools, environment, time limits, and retry rules before testing.

How to build a realistic test set. Use representative historical issues and merged PRs. The webinar suggests a pilot of 30–50 examples, recreated at their starting commits with solutions hidden. Verify the original fixes pass.

How to compare models fairly. Use your current setup as the baseline and compare one or two relevant open models with the same tasks, tools, harness, and budgets. Record the served model and test tuning separately.

How to verify success. Require target and regression checks. Review patches and traces, use judges for rubric-based assessments where useful, and count tool failures, timeouts, and exhausted budgets as failures.

How to measure cost and speed. Divide all attempt costs, including failures and fallbacks, by accepted tasks. Measure time to verified completion, and include review effort when assessing economics.

How to choose and improve the system. After meeting the quality threshold, compare cost, time, consistency, and failure severity. Inspect misses, repeat runs, use held-out tasks after tuning, and evaluate the full routing policy.

Learn how to choose an open model for a coding agent by measuring whether the complete system finishes representative work reliably, quickly, and economically. The central decision is which system fits which workload, rather than which model tops a leaderboard.

Based on Baseten’s 47 minute webinar, hosted by Alex Ker with Molly Elfers. Read the core explanation and worked examples in about 12 minutes; the three understanding checks are optional. What you are actually evaluating

A model generates reasoning, text, and tool requests. A harness runs the agent loop: supplies instructions, exposes tools, returns results, manages context, applies edits, and decides when to stop. A provider serves the model and handles requests, output formats, caching, and reliability.

A coding agent succeeds only when these parts work together. A sensible patch that never applies is a system failure. A correct tool request that the server misparses is also a system failure, even though the remedy differs.

Teaching model: measured quality depends on a configuration, not just a model name.

Q=Q(M,H,P,D,B,G)
Equation source
Q = Q(M,H,P,D,B,G)

Here M is the model, H the harness, P the serving configuration, D the task distribution, B the resource budget, and G the grader. Change one of these and you have changed the experiment. “Model A scored 80 percent” is incomplete without this context.

Start with the work and the acceptance rule

The webinar’s pilot keeps an existing harness and uses historical work from the team’s repositories: 23:39 to 28:23. Its chapter outline proposes 30–50 canonical PRs, meaning representative examples of recurring work. This is a starting pilot size, not a statistical guarantee.

Worked example for a solo builder: suppose your agent repeatedly fixes data ingestion bugs. Give each candidate the same broken starting repository and issue description. Ask it to repair the behavior and verify the fix. The acceptance rule is determined before looking at any candidate’s output.

Work you need Evidence that would support success
Repair a CSV import bug The failing input now imports correctly and existing import behavior still works
Add a settings screen Required controls work, persistence behaves correctly, and existing navigation still works
Review a pull request Findings identify real defects with evidence; false alarms are recorded
Answer a repository question The explanation points to the relevant code and accurately describes its behavior

These are teaching examples. Each needs its own grader; a test of isolated function generation cannot establish how well an agent navigates and repairs a real repository.

A target check asks whether the requested behavior works. A regression check asks whether previously working behavior still works. For the CSV fix, include existing tests for quoted commas, blank fields, and supported encodings. Running these checks after the patch catches a “fix” that repairs one input by breaking another.

A small evaluation contract

# Teaching template; choose values for your own workflow.
workload: repository bug fixes
baseline: your current model and harness
challengers: one or two supported open models
environment: pinned starting commit and dependency image
agent_tools: [read_files, search, edit, run_tests]
network: explicitly defined before the run
limits: fixed time, token, and attempt budgets
acceptance: target tests plus regression checks and patch review
logging: served model, tool calls, tokens, cost, elapsed time
comparison: same task set and declared retry policy

Baseten’s written guide adds important controls: validate that the original fix passes your grader, keep solutions and held out evaluation tests inaccessible to the agent, log the model actually served, and report tuned configurations separately. Use supported templates and tool interfaces rather than forcing every model through an incompatible format.

Why this matters: if the grader rejects the known correct solution, or the agent can read the solution commit, the experiment cannot answer your question.

Compare useful outcomes rather than token prices

The webinar calls out cost and wall clock per successful task at 29:01. The key denominator is an accepted outcome.

Illustrative example with 100 distinct tasks and one attempt each:

Measure Candidate A Candidate B
Cost per attempt $0.10 $0.30
Accepted tasks 25 90
Total inference cost $10 $30
Cost divided by accepted tasks $0.40 $0.33

B costs three times as much per attempt but costs less per accepted task. It also completes far more of the workload. A lower cost per success alone is insufficient if a candidate fails your quality requirement.

p^=accepted tasksattempted tasks,Cresolved=cost of all attemptsdistinct tasks resolved
Equation source
\widehat{p}=\frac{\text{accepted tasks}}{\text{attempted tasks}},\qquad
C_{\mathrm{resolved}}=\frac{\text{cost of all attempts}}{\text{distinct tasks resolved}}

Count failed attempts in the numerator. If your policy allows retries, count an eventually resolved task once and include every attempt’s cost. With no resolved tasks the ratio is undefined; it is never zero.

See why fast tokens can still mean a slow agent

The webinar distinguishes TTFT, latency, throughput, and cache behavior at 10:48.

TTFT, or time to first token, measures how soon a response begins. Output throughput measures tokens generated per second. Task completion latency measures when a verified result becomes usable. An agent can start quickly and generate rapidly while spending many turns searching irrelevant files or retrying edits.

Teaching approximation for a sequential agent loop:

Ttask≈∑j=1k(Tqueue,j+Tprefill,j+Nout,jrj+Ttool,j)+Tverification
Equation source
T_{\mathrm{task}}\approx\sum_{j=1}^{k}\left(T_{\mathrm{queue},j}+T_{\mathrm{prefill},j}+\frac{N_{\mathrm{out},j}}{r_j}+T_{\mathrm{tool},j}\right)+T_{\mathrm{verification}}

Here k is the number of model turns, r is output tokens per second, and tool time includes activities such as repository search and test execution. Faster generation reduces only one term; fewer unnecessary turns can reduce several.

For interactive work, inspect completion latency and its slow tail. For parallel batch work, also measure accepted tasks per hour at a stated concurrency. Summed attempt durations divided by successes is amortized elapsed effort; it is different from a user’s wait for an individual task.

Cache hits can lower repeated context processing cost or latency under a provider’s cache rules. Compare the actual workload bill and completion times. A high cache hit rate does not establish that more tasks were solved.

Separate a controlled comparison from a tuned system

The webinar’s initial pilot is “keep the harness, swap the model” at 24:22. This makes the first question interpretable: does changing the model improve your existing workflow?

A second experiment can ask whether changing the harness, prompt, or context strategy improves a particular model. Both questions are useful. They need separate labels.

Experiment Keep comparable What the result means
Initial model comparison Tasks, environment, tools, budgets, grader, retry policy Fit within the chosen workflow
Model specific tuning Final acceptance criteria and evaluation tasks Quality of the optimized system
Provider comparison Model version and supported request settings Serving effects under measured conditions
Routing comparison Workload and end to end acceptance rules Quality and economics of the complete routing policy

Failure diagnosis example: the agent attempts a valid file edit but the parser rejects the tool call. Check formatting and the tool round trip before concluding the model cannot code. Keep that failure in the system result; explain its cause rather than silently discarding it.

An LLM judge appears in the webinar at 28:23. Teaching guidance: use a judge for rubric based assessment where it helps, such as explanation quality or review usefulness. For executable behavior, retain test and execution evidence. Calibrate subjective judgments against human reviewed examples; another model’s approval is not independent proof of correctness.

Read small score differences carefully

Statistical teaching addition: on 30 tasks, a single changed result shifts the success rate by 3.33 percentage points. Comparing 25/30 with 26/30 does not justify a confident universal ranking.

For an illustrative binomial model, 25/30 gives an approximate 95 percent Wilson interval of 66.4 to 92.7 percent. That interval assumes independent tasks from a relevant population; correlated or selectively chosen tasks weaken the interpretation. It describes uncertainty about this sampling model, not all possible coding work.

Inspect paired outcomes: which tasks does A solve that B misses, and vice versa? Repeat runs to study variability on fixed tasks. Add representative tasks to improve workload coverage. These resolve different uncertainties.

If you optimize prompts against the pilot, use fresh held out tasks for the final decision. Otherwise you may have improved your benchmark fit more than your agent.

Shortlist with the frontier then choose by workload

At 17:14, the webinar uses Artificial Analysis for shortlisting; at 19:01, it introduces the Pareto frontier.

Teaching example: A costs $0.20 per accepted task at 75 percent success. B costs $0.30 at 90 percent. C costs $0.40 at 80 percent. Considering only these two metrics, B dominates C: it is cheaper and more successful. A and B remain tradeoffs. A quality floor of 85 percent excludes A.

A public frontier helps you select candidates to investigate. Your own task distribution, latency requirements, and failure severity determine the eventual choice.

The webinar’s “fleet engineering” discussion at 33:01 to 35:12 proposes matching workloads to models, including a mix of open and closed systems. The following routing diagram is a teaching reconstruction, not a prescribed vendor configuration.

The subtlety: a router is another system to evaluate. Include misclassification, fallback attempts, verification, and human intervention in its totals. A cheap first attempt followed by an expensive fallback can cost more than starting with the fallback.

The webinar also discusses Jevons paradox at 21:38. Teaching arithmetic: total spend equals usage multiplied by unit cost. If unit cost halves but usage triples, spend rises 50 percent. Separate efficiency gains from your decision to run more work.

A decision card you can reuse

You do not need to run an evaluation to use this card. It also helps you interrogate someone else’s model claim.

WORKLOAD: Which recurring tasks and repositories does this cover?
SYSTEM: Exact model, provider, harness version, tools, and limits?
QUALITY: Accepted count / task count; regressions and critical failures?
CONSISTENCY: Which results change across repeated runs?
COST: All attempts and fallbacks / distinct accepted tasks?
TIME: Time to accepted completion; slow tail; declared concurrency?
DECISION: Meets the quality floor and improves a relevant constraint?
EVIDENCE: Reproducible configuration, patches, traces, and grader?

For your solo AI projects: engineer review time can outweigh token savings. As a teaching extension, add inference, compute, and review costs before dividing by accepted tasks. An agent that saves $1 in tokens but creates ten extra minutes of debugging may be a poor economic choice.

Three quick understanding checks

  1. An open model has half the token price. Should you switch? Only after checking task success, total token use, retries, latency, and review effort under your workflow.
  1. A patch passes the new bug test but breaks an existing import test. Is it resolved? No. The target behavior improved, but the regression gate failed.
  1. An optimized challenger beats your baseline after changing both model and harness. What have you learned? The new system performed better under the measured protocol. You have not isolated the model’s contribution.

What to explore next

The highest value follow up is failure attribution: when a coding agent fails, was the cause its reasoning, missing context, tool execution, serving behavior, budget, or grader? This turns evaluation into a method for deciding what to improve.

A second useful question is whether a simple workload rule can match a complicated model router. Evaluate the extra routing complexity against accepted outcomes, including the cost of fallback.
